# Что изменилось при переезде с Node.js на Python

## Стек

| | Было (Node) | Стало (Python) |
|---|---|---|
| Сервер | Express | FastAPI |
| БД-драйвер | `node:sqlite` (встроенный) | `sqlite3` (встроенный) |
| ASGI/HTTP-сервер | — | Uvicorn |
| Склады | 2, изолированные | 1 |
| Параллельные рабочие потоки | 2 (по складу) | до 20 (по станциям) |
| Упаковка для развёртывания | требовался Node.js на сервере | единый `.exe`, ничего не ставить |

## Главное архитектурное решение: станция вместо склада

В двухскладской версии инвариант "не более одного открытого набора
одновременно" был привязан к складу — это работало, потому что на складе
подразумевался один физический поток сборки. С 20 станциями на одном складе
этот же инвариант, если оставить его "на склад", заблокировал бы 19 станций
из 20 в любой произвольный момент — почти всегда среди 20 работающих
одновременно операторов у кого-то набор в процессе.

Поэтому инвариант перенесён **на станцию** (`station_id` — свободная строка,
не предустановленный список, см. README): каждая из 20 станций ведёт свой
набор полностью независимо. Короб и паллета остались общим пулом склада —
закрытие короба забирает все закрытые-но-неупакованные наборы от **любых**
станций, не только от той, что сканирует агрегат короба. Единственная
проверка, оставшаяся привязанной к конкретной станции при закрытии короба, —
что у **этой же** станции не осталось незакрытого набора (иначе он молча
потерялся бы из партии — та же защита от "перепрыгивания шага", что и
раньше, просто в разрезе станции, а не склада).

## Модель конкурентности — заново, не портирование "один в один"

Node-версия была однопоточной (JS event loop) — это само по себе исключало
гонки между "параллельными" запросами: пока обрабатывается один скан, другой
физически не может начать выполняться. Python + FastAPI так не работают:
синхронные роуты выполняются в пуле потоков ОS, то есть **реальный
параллелизм есть**, и наивный порт логики "как было" содержал бы гонки.

Решение — одно соединение SQLite на процесс (WAL, `busy_timeout`) плюс
`threading.RLock()`, сериализующая все обращения к БД. Один скан
обрабатывается **одной непрерывной транзакцией** от проверки на дубль до
записи результата — без разрывов между захватами блокировки. Это нашлось
не сразу: первая версия делала проверку дубля и запись как два отдельных
захвата блокировки, и это реальная гонка при 20 потоках — переделано на
единую транзакцию до передачи в тестирование.

### Результаты нагрузочных тестов (см. историю сессии за точными командами)

**Тест 1 — намеренная гонка.** 20 потоков одновременно сканируют один и тот
же код (`threading.Barrier`, чтобы стартовать максимально синхронно):
результат — код принят ровно 1 раз, 19 честных ошибок "дубль". Блокировка
держит гонку железно.

**Тест 2 — 20 станций, полный цикл, in-process.** 20 потоков, каждый гонит
свой цикл товар→товар→агрегат набора (500 наборов, 1500 сканов) параллельно:
0.46 сек, 3232 скана/сек суммарно, 0 неожиданных ошибок бизнес-логики.
Целостность после теста проверена по 6 независимым критериям (количество
товаров/наборов, соответствие items_count/items_required, station_id не
расползается между items и их набором, нет дублей km_code) — 0 расхождений
по всем.

**Тест 3 — 20 станций через настоящий HTTP.** То же самое, но уже реальными
сетевыми запросами к живому Uvicorn (900 сканов): 1.89 сек, 477
HTTP-сканов/сек, 2.1 мс/скан в среднем — с учётом полного круга (TCP,
JSON-сериализация, диспетчеризация в пул потоков, транзакция БД, JSON-ответ).
0 ошибок. Каждая из 20 станций закрыла ровно по 15 наборов — идеальное
распределение, без перекосов и коллизий.

Реальный складской темп на порядок ниже (человек физически не сканирует
быстрее ~1 кода в секунду) — запас по пропускной способности on order 20-70x.

## Упаковка в `.exe`

Разделены два понятия путей (`app/paths.py`):
- `resource_dir()` — файлы, вшитые внутрь exe (schema.sql, дефолтный
  kit-templates.json, public/) — только для чтения, при заморозке
  распаковываются во временную папку PyInstaller.
- `app_dir()` — данные (БД, бэкапы) — обязаны жить рядом с exe-файлом, а не
  во временной распаковке, иначе исчезали бы при каждом перезапуске.

`build_exe.spec` реально протестирован сборкой (пусть Linux-бинарник —
механизм идентичен, PyInstaller не кросс-компилирует между ОС, сам `.exe`
для Windows нужно собрать на Windows-машине по инструкции в `build_exe.md`).
Проверено на собранном бинарнике: запуск из директории, отличной от
расположения exe (пути резолвятся от `sys.executable`, а не от cwd), приём
сканов, раздача фронтенда из вшитых ресурсов, автобэкап при старте, и
отдельно — чистая обработка битого `kit-templates.json` (понятная ошибка,
exit code 1, никакого мусора в БД) — именно так же, как в обычном
`python run.py`.

## Что осталось без изменений

- Бизнес-логика валидации сканов (Этап 2 плана) — тот же алгоритм.
- Формат выгрузки для ТО — те же 4 колонки.
- Философия автобэкапа — периодически + при старте, ротация последних N копий.
- Внешний вид и структура интерфейса — тот же тёмный дизайн, те же три
  вкладки, тот же принцип тестовых "чипов" для сканирования без реального
  сканера.
- Валидация `kit-templates.json` при старте с понятными ошибками вместо
  сырого стектрейса — перенесена как есть, включая проверку "не GTIN ли это
  случайно вставленный полный КМ".
