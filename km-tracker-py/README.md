# КМ-трекинг — один склад, до 20 станций (Python/FastAPI/SQLite)

Локальный сервер учёта иерархии КМ (товар → комплект → короб → паллета) для
одного склада с параллельной работой до 20 рабочих станций. Порт с
Node.js-версии на Python + FastAPI + SQLite (см. `CHANGES_FROM_NODE.md` за
подробностями и обоснованием ключевых архитектурных решений).

## Ключевая идея: станции вместо складов

20 операторов работают **одновременно и независимо** — каждый ведёт свой
набор. Короб и паллета — общий пул склада: любая станция может закрыть
короб, и он заберёт закрытые наборы от **всех** станций, а не только от
"своей". Подробнее — в `CHANGES_FROM_NODE.md`.

`station_id` — не логин и не список из 20 предустановленных станций, а
свободная строка, которую браузер конкретного ПК запрашивает один раз при
первом заходе и хранит у себя (localStorage). Ничего заранее настраивать
не нужно — просто открываете страницу на каждой из 20 станций и вводите
любое понятное имя ("Стол 5", "Иванов", что угодно).

## Установка и запуск (разработка / обычный Python)

Нужен Python 3.11+.

```bash
pip install -r requirements.txt
python run.py
```

Сервер поднимется на `http://0.0.0.0:8000` — то есть доступен и с этого
компьютера (`http://localhost:8000`), и с любого другого ПК в той же
локальной сети (адрес печатается в консоли при старте). Именно этот адрес
нужно открыть в браузере на каждой из 20 станций.

## Сборка в один `.exe` (для развёртывания без Python на сервере)

См. `build_exe.md` — пошаговая инструкция, уже проверенная реальной сборкой
(см. файл за подробностями, что именно было протестировано и как).
Итоговый `km-server.exe` самодостаточен: копируете один файл на серверный
ПК склада, запускаете — Python и зависимости устанавливать не нужно.
Станции по-прежнему работают через обычный браузер, ничего не устанавливая.

## Конкурентность: как 20 станций не мешают друг другу

Модель нарочно простая и предсказуемая, а не максимально параллельная:

- Одно соединение SQLite на процесс, WAL-режим, `busy_timeout`.
- Одна `threading.RLock()` сериализует **все** обращения к БД — и чтения,
  и записи. При складском темпе сканирования (не сотни операций в секунду
  с одной станции) это не создаёт очереди, зато полностью исключает гонки
  между потоками (FastAPI выполняет синхронные роуты в пуле потоков ОС —
  это НЕ однопоточный Node.js, гонки были реальны, пока не свёл всю
  обработку одного скана в одну транзакцию).
- Один скан = одна непрерывная транзакция от проверки дубля до записи
  результата — без разрывов между захватами блокировки.
- UNIQUE-констрейнты в схеме (глобальная уникальность любого кода,
  не более одного открытого набора на станцию) — независимая вторая линия
  защиты на уровне самой БД, а не только в коде приложения.

**Проверено тремя нагрузочными тестами** (подробности и цифры —
`CHANGES_FROM_NODE.md`): 20 потоков одновременно сканируют один и тот же
код → принят ровно 1 раз; 20 станций параллельно проходят полный цикл
товар→набор in-process — 0 расхождений целостности; то же самое через
настоящий HTTP — 477 сканов/сек, 2.1 мс/скан, снова 0 расхождений, ровно
поровну наборов на каждую станцию.

## Резервное копирование

- Автоматически каждые 15 минут + при каждом старте сервера →
  `data/backups/km_ГГГГММДД_ЧЧММСС.db`
- Хранятся последние 60 копий (~15 часов при интервале 15 минут — если
  нужна более длинная история, скопируйте `data/backups/` на внешний
  диск/сетевой ресурс дополнительно, сервер это делает только локально)
- Ручной бэкап: `curl -X POST http://localhost:8000/api/backup`
- Восстановление: остановить сервер, скопировать нужный файл из
  `data/backups/` в `data/km.db`, запустить снова

## Тестовый прогон / очистка

```bash
python -m app.reset
```

Спросит подтверждение, сотрёт все сканы, сохранит справочник наборов.

## Справочник наборов

`app/config/kit-templates.json` — редактируемый JSON, тот же формат, что и
в Node-версии. GTIN — 14-значный (13-значный EAN-13 дополняется одним нулём
слева). Настоящий код маркировки (КМ) сюда не вписывается — он приходит
только при сканировании и целиком сохраняется в БД, конфиг работает только
с GTIN товара/набора как типа продукции. Валидация при старте (дубли GTIN,
формат, обязательные поля) не даст серверу подняться с битым конфигом —
вместо стектрейса будет понятное сообщение, что именно поправить.

## Структура проекта

```
km-tracker-py/
  run.py                  — точка входа (обычный запуск и .exe)
  build_exe.spec           — PyInstaller spec (проверен реальной сборкой)
  build_exe.md              — инструкция по сборке под Windows
  requirements.txt
  app/
    main.py                 — FastAPI-приложение, все роуты
    db.py                    — SQLite: WAL, блокировка, транзакции, сидирование
    paths.py                  — разрешение путей (важно для .exe)
    validation.py              — бизнес-логика сканирования
    control.py                  — дерево контроля, поиск, статистика
    report.py                    — выгрузка для ТО
    backup.py                     — автобэкап
    reset.py                       — очистка для тестового прогона
    config_validate.py              — валидация kit-templates.json
    schema.sql                       — схема БД
    config/kit-templates.json         — редактируемый справочник наборов
  public/
    index.html, app.js       — интерфейс (адаптирован под одну станцию)
  data/
    km.db                     — рабочая БД (создаётся автоматически)
    backups/                    — автоматические резервные копии
```

## Известные ограничения

- Дерево во вкладке «Контроль» строится целиком при каждом запросе, без
  пагинации — комфортно до нескольких тысяч наборов, при десятках тысяч
  стоит добавить постраничную загрузку.
- `station_id` — не аутентификация: любое устройство в локальной сети может
  представиться любым именем станции. Для складского контура на доверенной
  локальной сети это осознанный компромисс в пользу простоты ("не
  использовать лишние зависимости" — полноценный логин потребовал бы
  отдельного модуля пользователей).
